# 企业招聘信息采集方案

状态：已确定。日期：2026 年 10 月 10 日。

采用**适配器主导的确定性采集方案**：以 Crawl4AI 为网页与浏览器执行基础，建立统一的采集、验证和导出流程；相同招聘平台尽量复用适配器，通过企业配置区分入口和招聘范围。AI 辅助探索、开发与修复，正式任务使用经过验证的适配器版本。

本方案优先保证已接入站点的覆盖范围可核对、错误可定位、过程可复现。新站点需要一次开发接入；已有适配器是否可以直接复用，须经验证后确定。新增网站和网站改版都可能产生维护工作。

## 决策依据

此前验证分为固定适配器采集和陌生网站自主探索两部分。固定适配器基线曾导出 6,650 条记录；该结果只代表当时四个站点及其指定范围，不能证明对陌生网站的自动适配能力。

陌生站点最终复测只导出国家能源 1 条、中国邮政总部 8 条，腾讯 0 条，三站均未通过全量验收。主要问题包括分页失败后的无效重试、多单位目录未遍历、页面资源访问失败，以及将局部目录完整误报为整个任务完成。测试网站通过不能替代这些真实站点的验收。

因此，正式采集的路径、分页、目录遍历和完成条件由适配器明确表达，AI 生成的规则须经过开发验证后才能进入正式流程。自主探索原型保留为开发工具，不承担正式采集的完整性保证。

实验依据保存在 `validation/crawl4ai-campus` 分支的提交 `462513b`，重点文件为 `docs/autonomous-validation.md`、`validation/autonomous-20261010/`；固定适配器基线提交为 `73f40b9`。

## 采集目标与范围

第一阶段覆盖用户提供的企业官方招聘入口及其实际指向的招聘平台，默认采集正式校园招聘，排除社会招聘和实习。不同招聘批次、地区、单位及子单位必须分别确认是否纳入，不能默认只采首页推荐或一个分公司。

默认保留指定公开目录中仍可见的已截止岗位，并记录截止日期和源站状态。如果业务只需要可申请岗位，应作为明确的筛选条件执行；不能静默删去已截止岗位，再将剩余数量与整个目录的总数比较。

用户提供企业和入口，开发负责接入与维护。岗位数据全部由程序读取，CSV、JSON 和 Excel 表格由程序导出，不手工补录或修正岗位内容。缺失字段保留为空并说明原因。

本阶段不承诺任意 URL 的零配置全量采集，不实现自动投递、注册或验证码破解。登录后的数据仅在站点接入方案明确、具备用户授权的会话时采集；没有会话则报告受限范围。

## 用户输入与站点清单

最小输入是“企业名和招聘入口 URL”。优先级、校招或其他招聘范围、已知登录要求可以一并提供。尽可能早地提供完整清单，有助于识别可复用平台和安排接入顺序；后续可以持续追加，不要求一次列全。

平台识别、适配器选择、接口参数和分页规则属于开发工作，不要求用户提供。相同域名不一定使用相同系统，同一第三方平台的不同版本也需要分别验证。

站点清单至少记录以下信息：

| 信息 | 用途 |
| --- | --- |
| 企业标识与名称、入口 URL | 稳定标识来源，保留入口变更历史 |
| 招聘类型、批次、纳入与排除范围 | 定义任务边界和计数口径 |
| 优先级 | 安排接入与维护顺序 |
| 平台、适配器及版本 | 由开发识别、验证并绑定 |
| 登录与附件要求 | 说明访问条件和当前解析能力 |
| 接入状态、最近验收与失败原因 | 区分未接入、验证中、可运行和需修复的站点 |

## 架构与职责

执行流程为：加载企业配置和字段要求，解析招聘范围，生成目录与详情任务，执行读取，归一化数据，核对覆盖和字段，最后导出结果及报告。

| 模块 | 职责 | 设计约束 |
| --- | --- | --- |
| 站点配置与适配器注册 | 企业入口、范围、适配器版本和执行预算 | 使用显式绑定，避免正式任务猜测适配器 |
| Crawl4AI 执行层 | 渲染、会话、页面操作、请求及资源读取 | 会话隔离，限制并发、超时和重试 |
| 平台适配器 | 目录发现、筛选、分页、详情关联和字段解析 | 明确输入、输出与完成条件，优先跨企业复用 |
| 企业配置与必要扩展 | 租户参数、招聘类型、批次及特殊页面差异 | 能用配置表达时不复制整套适配器 |
| 任务队列与检查点 | 单位树、批次、列表页、详情、附件等任务状态 | 持久化待办、成功、失败及排除理由 |
| 数据与证据层 | 统一岗位模型、字段来源、原始响应和记录版本 | 保存源站标识，支持离线复核 |
| 验证与导出层 | 数量、唯一键、覆盖范围、字段检查及表格生成 | 完整和部分结果必须明确区分 |
| AI 开发工具 | 探测、解释响应、生成适配器草稿和修复候选 | 经验证后纳入版本管理，不直接替换正式流程 |

采集优先使用实际观察并验证过的公开数据接口，其次使用 HTML 列表和详情，再使用浏览器交互。PDF 等附件按已实现的解析能力处理；无法解析的附件作为未完成任务报告，不能把它们当成无岗位内容。

浏览器和接口读取复用 Crawl4AI 会话；执行层统一封装，适配器不自行创建相互独立的 HTTP 客户端。资源下载、认证状态和请求错误都纳入证据记录。

初版使用 Python CLI 和 SDK，使用 SQLite 保存运行、任务和记录索引，原始证据存文件系统。先以单机任务队列实现可靠运行；需要时再扩展调度或多机执行，初版不引入分布式系统。

## 适配器与配置的边界

平台适配器描述相对稳定的系统行为，例如目录结构、页码或游标、岗位唯一键、详情参数关联，以及接口字段含义。企业配置描述入口、租户、招聘类型、批次、地区、单位和业务筛选条件。

配置不承载任意可执行代码。复杂的单位树遍历、签名计算或页面流程应封装为可测试的适配器逻辑；有充分共同点后再抽成共享能力，不为了复用把明显不同的平台强行合并。

适配器的职责接口约定如下，具体 Python 类型在实现阶段定义：

| 操作 | 输出及要求 |
| --- | --- |
| 检查入口 | 确认平台特征、页面可读性、登录状态和能力缺口 |
| 枚举招聘范围 | 返回批次、单位及子单位任务，保留父子关系和排除理由 |
| 枚举岗位 | 返回列表记录、分页位置、源计数及终止依据 |
| 读取详情 | 按已验证参数关联详情和附件，不将公告等同于岗位 |
| 解析记录 | 转为统一字段，并保留原始标识、原文和字段来源 |
| 校验范围 | 返回覆盖计数、失败任务、缺失字段及完成判定 |

任务键至少区分站点、招聘范围和源对象。列表和详情的参数必须保留相关联的单位、批次等信息，不能只替换岗位 ID 而误用其他记录的参数。

队列必须能够表达“单位 A 已完成、单位 B 的第三页失败、单位 C 的附件待处理”。看到单位 A 的总数吻合，不得将整家企业标记为完成。

## 字段与数据模型

统一保存岗位的企业、招聘单位、岗位名称、招聘类型与批次、工作地点、学历、专业、招聘人数、职责、任职要求、公告通用要求、发布时间、截止日期、源站状态、详情与投递链接、源岗位标识及采集时间。

用户可以选择导出字段；新增字段需要先检查已有原始数据和适配器支持情况。描述字段并不意味着所有站点都一定存在该字段。接入验收时明确必填字段和可选字段，默认将岗位名称、企业、来源和任职要求列为必填要求；若源站确实不提供，应报告字段缺失，不用推断值通过验收。

数据处理遵循以下规则：

- 使用源站岗位标识及必要的单位、批次构成稳定唯一键，不能只按岗位名称去重。跨平台的相似岗位先保留各自来源，不直接合并。
- 招聘启事包含多个岗位时展开为多行，公告级要求另行保留，并与岗位关联；分别统计公告数量与岗位数量。
- 人数保留“若干”等原文；没有业务含义证据时，不将接口的零值自动解释为缺失。没有提供的日期为空，不把更新时间当作发布时间。
- 记录每个字段的来源路径、选择器或原文引证；原文和必要的标准化值分开保存。
- 保留首次发现、最近出现和本次采集时间。只有覆盖检查通过的运行才能据“本轮未出现”判断岗位可能下架；不完整运行不得触发批量下架。

## AI 的使用方式

模型统一使用 `deepseek-flash`，密钥从环境变量读取，不写入配置、日志或版本库。

开发阶段允许 AI 根据网页、控件及网络证据选择下一步操作，辅助发现入口、接口和字段，生成适配器草稿、测试样例和修复候选。开发将这些产物变为明确规则，再通过回放和真实站点验收。

正式运行的导航、分页、筛选、单位遍历及完成判定均执行固定流程。对于确实无法以稳定规则解析的非结构化正文，可以在该站适配器明确启用 LLM 抽取；必须提供原文引证、字段校验、模型版本及调用预算，失败后保留原文并报告。它不能替代覆盖检查。

检测到改版时，程序停止受影响范围或输出部分结果。AI 可以生成修复建议；修复经检查、测试和站点验收后发布新版本，不在运行中直接改写生产适配器。

## 完整性与运行状态

完整性针对事先声明的招聘范围，而非无法穷尽的整家企业互联网内容。每次运行必须输出入口、纳入和排除的类型、批次、地区、单位、统计时间及访问限制。

| 状态 | 判定 |
| --- | --- |
| complete | 所有应采范围及任务已处理，分页有终止依据，数量与唯一键核对通过，必填字段满足要求 |
| partial | 已获取岗位，但存在未处理范围、失败详情、附件障碍、必填字段缺失或无法证明覆盖完整 |
| blocked | 没有可交付岗位，或入口、会话、解析能力等问题阻止采集 |

没有源站总数时，需要适配器提供可复核的结束依据，例如目录已穷尽、游标明确结束或经过验证的最后一页状态。无法提供依据则保持 partial。源站明确显示范围内零岗位，且目录遍历完成时，可以输出 complete 和零条记录。

总数、页数、唯一记录数、详情关联和分支覆盖分别检查。源计数与程序计数采用相同筛选口径；过滤前的目录数、排除数和最终输出数分别报告。任何未完成范围都不能被最后一次成功采集覆盖掉。

数量变化、重复页、重复游标或缺失详情会触发有上限的重试。网站不是事务快照，记录采集时段；变化持续存在时输出 partial，不能反复重试到预算耗尽后宣称成功。

保留通过校验的部分岗位，并列出失败任务、错误类别、来源 URL、已尝试操作和继续执行需要的条件。`partial` 和 `blocked` 必须能被调用方识别为未完成；计划中的 CLI 对这两类状态返回非零退出码。

## 执行与导出要求

按域名控制请求速率、浏览器数量及并发，配置请求、页数、模型调用和总运行时间预算。详情分批读取和解析，及时释放页面与解析树，不一次性把全部详情留在内存。

检查点绑定适配器版本、站点配置、任务参数和采集时间。恢复任务时先验证这些条件和入口有效性，列表不能无条件复用旧缓存，避免将历史数据与当前目录混为一轮完整结果。

初版由 Python 程序导出 CSV、JSON 和 XLSX。工作簿包含岗位、覆盖情况和失败任务三个工作表；JSON 保存完整正文和证据引用，表格中的超长正文须有明确的截断提示和对应完整数据位置。CSV 与 XLSX 防止源站文本被解释为公式。

每次输出包含运行标识、代码与适配器版本、站点配置、采集时间、字段缺失统计、完整性状态和错误摘要。原始响应与附件独立保存，日志和可共享报告对凭据及会话材料脱敏；大型运行产物不进入 Git。

## 新站接入与日常维护

1. 将用户提供的企业和 URL 加入清单，明确招聘范围与字段要求。
2. 用可复现的探测程序确认平台、入口、目录、详情及登录条件；AI 可辅助探索，采集证据由程序保存。
3. 选择已有平台适配器，或开发新适配器。将能复用的行为留在平台层，将企业差异放入配置或小范围扩展。
4. 先验证一页列表和一条详情，再检查第二页、末页、其他单位、公告展开及附件等实际存在的路径。
5. 完成全范围试运行，核对源计数、唯一键、目录任务、必填字段和输出；验证部分失败时能正确报告并保留有效记录。
6. 将脱敏回放样本、适配器版本和验收结果一并提交。通过后将该站标记为可运行，后续任务使用明确版本。

维护重点包括页面结构、接口模式、目录数量、字段覆盖率、错误率和任务耗时的变化。数量下降是调查信号，不能单独判定采集错误或真实下架。

登录过期、验证码、资源 403、规则解析错误、源站数据变化及预算耗尽使用不同的错误类别。公开岗位可读、只有投递需要登录时，继续采集公开内容；确实无法读取的范围明确报告，不承诺所有第三方系统都能自动处理。

## 工程与测试约定

Python 项目由 uv 管理依赖和锁文件，使用 Ruff 检查与格式化、ty 做类型检查。实现时提供以下验证命令：

```sh
uv sync --locked
uv run ruff check .
uv run ruff format --check .
uv run ty check
uv run python -m unittest discover -v
```

上述命令属于后续工程约定，当前仅包含方案文档的 main 尚未提供可运行的采集项目。

测试分为公共执行能力测试、适配器脱敏回放测试和真实站点验收。重点覆盖分页重复、源总数变化、单位遍历遗漏、详情绑定错误、字段缺失、登录失效和断点恢复。验证一个分公司不能代表整站，验证一次成功也不能替代改版后的复验。

后续代码组织约定：

```text
src/job_crawler/
  core/         # Crawl4AI 会话、执行预算、队列和重试
  adapters/     # 平台适配器及必要的企业扩展
  models/       # 岗位、范围、任务、运行和证据模型
  validation/   # 覆盖与字段核对
  exporters/    # CSV、JSON、XLSX
  devtools/     # 探测、AI 辅助开发和回放工具
sites/          # 企业配置，不包含密钥或会话凭据
tests/          # 公共能力与适配器测试
docs/           # 方案、接入说明和验收记录
```

## 实施顺序与验收

| 阶段 | 工作 | 完成条件 |
| --- | --- | --- |
| 公共基础 | 整理统一模型、Crawl4AI 执行层、队列、证据、状态及导出 | 能报告失败并恢复任务，能区分局部与完整结果，静态检查和公共测试通过 |
| 迁移已有基线 | 按本方案整理平安、建行、中石油、阿里四站逻辑 | 每站重新进行真实全范围验收，不沿用旧行数作为当前成功证明 |
| 接入新增三站 | 完成国家能源分页、中国邮政单位树和腾讯入口及详情适配 | 逐站声明范围、完成覆盖核对；确实受限的站点单独列出，不能以成功站点掩盖 |
| 扩展站点与维护 | 按用户清单归类平台、复用适配器、补充改版回放 | 新站接入有明确版本和验收记录，后续失败能够定位并修复 |

各阶段按可验证结果推进，不以固定开发天数承诺所有站点都能接入。调度频率和部署方式在站点与业务更新需求明确后配置，本次确定方案不启动定时任务。

## 分支与交付约定

`main` 保存本方案，并作为后续正式实现的基线。验证分支保留实验代码和证据；可复用模块经整理与验收后逐项引入，不直接将实验成功或原型能力视为正式验收结果。

后续每个站点的交付包括企业配置、适配器及版本、测试与验收记录，以及程序导出的岗位表、覆盖报告和失败明细。上线范围和仍需维护的障碍必须同时可见。
