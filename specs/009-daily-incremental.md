# SPEC-009 每日详情请求优化

状态：开发中。目标版本 `v0.0.1-alpha.2`（Python `0.0.1a2`）。

## 目标与边界

每日仍完整读取已接入来源的列表，减少不必要的详情请求，保持目录覆盖可核对。输入为来源/适配器、时间窗口、SQLite 历史及当前列表；输出为岗位快照、十二列表格、筛选依据与详情读取/复用/跳过计数。不依靠未验证的列表排序提前停止翻页，不新增 LLM 导航或定时调度。本轮真实请求量不作未经运行证明的承诺。

## 规则

- `day` 仍为 `[as_of-24h, as_of]`。已知列表发布时间明确早于窗口才跳过详情；日期按天提供时使用整天与窗口相交。未来、无效、缺失日期不能被当作旧日期。已明确截止可继续预筛选。
- 北森/建行使用已验证的列表日期字段。中石油缺少已验证的列表发布时间，按公告 ID 缓存展开岗位，不猜日期字段；平安/阿里列表已含正文，仍完整获取列表。
- 每来源建立带适配器/入口/代码身份的历史。每日列表未变化、上一完整目录仍出现、成功详情未满 15 天、证据可用时复用；列表变化、重新出现、缓存损坏/缺失/到期则重读。`all` 绕过跨轮详情缓存，作为全量刷新；week/month 保持原抓取方式。配置可关闭每日预筛选及复用，缓存期限可配置。
- 不用 first_seen 冒充 published。默认每日结果包含有可靠发布日期的窗口内岗位，以及无发布日期但在已建立基线后首次发现且发现时间位于窗口内的岗位，分别标记依据；可配置关闭无日期新增纳入。非空无法解析的发布日期保持待核验。
- 无历史时先建立基线：无日期存量不冒充新增；仍抓取并保存详情。只有目录完整、身份无重复且全部任务有交代才推进该来源历史；局部失败不推进基线/在场集合。丢失历史后重新建立基线，旧版数据库不凭不足证据自动迁移为可信详情缓存。
- 复用岗位保留原采集时间和证据，并附本轮列表证据；列表预筛选的记录标记仅列表。覆盖计数分开记录新读取、缓存复用、窗口跳过、过期跳过，不能把跳过伪称详情读取。公告计数与展开岗位计数分开。
- 导出、分类、汇总保留输入窗口，不允许每日快照静默变成全量；混合窗口汇总拒绝。每日正常生成严格导入表和包含待补全项的信息表。预筛选产生的简略行不能借改窗口冒充全量详情。

## 失败与验收

失败源保留本轮成功记录及问题，不使用历史记录掩盖本轮失败；不能证明有效的缓存回退到请求。成功但零岗位的目录仍可更新在场集合。无日期首次发现只表示发现时间，不保证真正发布时间；失败超过窗口后的自动补采和跨轮交付去重不在本轮实现。

测试覆盖冷启动、热缓存、列表变化、15 天边界、全量强制刷新、重新出现、坏缓存、日期未知/未来/边界、公告展开、局部失败、身份隔离和每日导出/分类窗口。用可计数回放请求比较优化前后输出及请求量；合成与历史字段回放不得标作实时验收。质量门禁 uv/Ruff/ty/pytest、构建及版本一致性通过后合并 main 并打附注标签。
